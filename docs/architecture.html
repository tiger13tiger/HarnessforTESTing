Figure 1

The promotion pipeline: dev → uat → main

Three Azure SQL databases, three git branches, two gates. One gate is a script; the other is a person — and, as of this review, a GitHub ruleset that actually enforces it (verified by pushing straight to main and watching it get rejected), not just convention. An unconditional test suite (Fig. 1 below the pipeline) watches all three branches regardless of which gate is in play.

automated human-reviewed auto-retry on failure validated, ready for a human out of scope
  • promote-dev-to-uat.yml: promote jobFires on every push to dev that touches procs/**.sql or tests/**.yaml. Loops over every entry in procs/manifest.yaml (harness/manifest.py) — not just one hardcoded procedure — deploying each to UAT inside its own transaction and running its validation suite, continuing past a failure to surface every broken procedure in one run. Only on a clean pass for every entry does it merge dev into uat and push.
  • promote-dev-to-uat.yml: validate-after-merge jobRuns only once promote succeeds, i.e. only after the merge actually landed. Re-deploys and re-validates every manifest entry against UAT using uat's own branch state — catches a merge-specific surprise (an odd conflict resolution, a database that drifted between the two checks) that validating the candidates alone, a moment earlier, couldn't see.
  • auto-fix-dev.yml (reusable)Called by whichever of the two jobs above failed. First runs harness/governance_check.py as a fail-fast CI step — but the real enforcement is one layer deeper: DeepSeekLLMClient.__init__ itself refuses to construct unless infra/deepseek_governance_approval.yaml has a real, filled-in sign-off, since DeepSeek is a China-based provider. That means a local run of evolve_cli.py --provider deepseek, or any future workflow that constructs this client, is blocked the same way — not just this one step's ordering. Then loops over the manifest; for each failing procedure, harness/metrics_log.py's next_round_for_proc() reads reports/metrics_log.jsonl for that procedure's own consecutive-failure count — each procedure has its own round number, not one shared across the manifest — and a procedure past round 3 is skipped (loudly, with its own ::error::) without blocking any other procedure's attempt. Procedures still in budget go to harness/evolve_cli.py --provider deepseek against dev (the same fix loop as Fig. 2), logging every attempt — converged or not — back to that same log (read by harness/metrics_cli.py for a success-rate/cost trend). Whatever converges gets committed with a per-procedure [auto-fix round N/3] tag (rationale rendered via harness/rationale_cli.py) — which re-triggers promote-dev-to-uat.yml from the top — even if other procedures in the same run didn't. This push uses a PAT, not the default token — a default-token push can't re-trigger a workflow, which would otherwise make this whole loop silently inert.
  • uat-to-prd-gate.ymlFires on every pull request into main — no path filter, unlike the other gates, because its validate job is a required branch-protection status check: a required check gated by a path filter never reports anything, and never stops being "pending," on a PR that doesn't touch that path. A git-diff step inside the job decides whether there's actually anything to validate — a real procs/**.sql/tests/**.yaml change re-validates against UAT for real; anything else (docs, workflow files, pure harness/**.py) passes on "nothing to validate" instead of leaving the reviewer's merge button stuck waiting forever. Either way it scans the PR's commits for an [auto-fix round tag and posts a comment flagging any LLM-generated fix, with its rationale — merging itself is still always a person's click, never automatic.
  • tests.ymlRuns the full unit suite on every push to dev/uat/main and every PR into main — no path filter, unlike the two gates above. Cheap enough to run unconditionally: pyodbc is imported lazily inside connector.py's methods, so the suite needs no ODBC driver installed. Exists because a code-only change to harness/**.py (no procs/**.sql or tests/**.yaml touched) used to skip both gates' pytest step entirely and reach main with zero automated coverage.
  • Where this stopsNothing past main is built yet. Getting a merged change into the actual production Synapse warehouse is still whatever your team's release process already is.

Figure 2

Inside one evolve() attempt

This is what runs on dev — by a person, or by evolve_cli.py asking an LLM for a fix. Up to 5 attempts. The transaction boundary and the guardrail-before-deploy order are the two decisions the whole safety story rests on. guardrails.py checks more than it used to: a second statement smuggled in after the procedure's own closing END, and a reference to any table on a PII blocklist, not just TRUNCATE/DROP targets. What's new and not shown as its own box below: right after the LLM responds, its rationale and SQL are scanned for anything that looks like an email/SSN/phone before either is stored anywhere — a leak is withheld, replacing the stored rationale with a placeholder, before it could reach a report or a public commit message. Every round that fails also records a one-line lesson (harness/lessons_log.py, deduped so a repeated failure doesn't spam the log) — a record for a human to read, never fed back into a future prompt automatically; see README.md's "Lessons log" section for why not.

normal path failed, retryable via LLM stops immediately, no retry pass
  • Why one transactionWithout it, a candidate that fails validation could still have partially overwritten a table before the loop asks for a fix. The rollback makes every failed attempt a no-op as far as the database is concerned.
  • Why typed stagesdeploy, exec, and validate get different repair guidance (llm_client.py's STAGE_GUIDANCE) — a syntax error and a wrong total are different problems, and the prompt says which one happened instead of one generic "it failed."
  • promote.py runs the same deploy → exec → validate → commit/rollback shapewith no LLM step and no retry loop — it's what promote-dev-to-uat.yml actually calls, since by the time a candidate reaches dev → uat it's already supposed to be fixed.
What happens to an LLM response before anything in Fig. 2 trusts it

Added after comparing this project against bank-data-agent-eval, a sibling harness built to attack an LLM agent. Two independent checks, every response, win or lose — neither existed before this review.

  • Why "withheld," not just "logged"The real rationale/SQL text is never assigned to Iteration.rationale when a leak is detected — harness/evolve.py replaces it with a placeholder before anything downstream (a report, a commit message) can see it. Catching a leak on the way out only works if nothing already wrote it down on the way there.
  • Why the lessons log doesn't feed back into the prompt by itselfA coincidental failure could get mistaken for a general rule with no one to catch it, and an unreviewed auto-promotion would turn a single bad response guardrails already discard into a standing instruction for every future fix. See README.md's "Lessons log" section for the full reasoning.

Reference

The seven check types validate() can run

Every workflow run is one YAML suite listing these by type. golden_rows is the one both evolve.py and promote.py actually use against business-verified figures; the rest exist for narrower questions.

typecatches
golden_rowsResult rows don't match a business-verified reference set, per dimension key and per-measure tolerance — the one used for "does this match what I checked in the pivot table."
aggregateA single calculated value (a total, a ratio) doesn't match a reconciled figure, or has drifted vs. a baseline query.
schemaA column renamed, retyped, or dropped between what's expected and what's actually there.
row_countRow count out of bounds, or drifted vs. a baseline environment beyond tolerance.
null_rateA key column filling up with NULLs beyond a threshold.
duplicatesA key that should be unique isn't.
pivot_readinessA measure column stored as text, or a dimension's cardinality/NULL rate that would break a pivot table downstream.

Honest status

What's actually been proven
verified

The full closed loop in Fig. 1 ran for real in CI, not just locally: a planted bug failed promote against live UAT, auto-fix-and-retry sent it to DeepSeek, the fix ([auto-fix round 1/3]) pushed via a PAT, re-triggered the workflow, passed, merged into uat, and validate-after-merge re-confirmed it — run #13.

verified

Getting there took three real bugs found and fixed by that same test: a transient-error classifier that never actually matched Azure's serverless-resume error (40613), a race between the two auto-fix-retry jobs, and a raw traceback instead of a clean error on a permanent connection failure.

verified

122 unit tests, including planted-defect cases proving each check catches what it claims to, plus regression tests for every bug found this way — with a mock LLM and mock connector, no live credentials needed. tests.yml now runs them on every push/PR with no path filter — previously promote-dev-to-uat.yml's own pytest step only fired on procs/**.sql/tests/**.yaml, so a 900-line, 22-file commit that was pure harness/**.py + workflow changes landed on main with zero CI coverage, caught only because pytest happened to be run locally first.

worth noting

DeepSeek's real fix passed by removing a join rather than de-duplicating it — a different, and arguably more correct, fix than the one originally shipped by hand. It passed because the synthetic seed data can't tell the two approaches apart (every store has ≥1 promotion by construction). An LLM fix passing golden checks doesn't mean it matches the original's exact logic — this is exactly why uat → main stays a human gate.

verified

No longer hardcoded to one procedure: every validate/promote/auto-fix step loops over procs/manifest.yaml. Every LLM call's token usage, estimated cost, and model id now gets logged to reports/metrics_log.jsonl for a success-rate/cost trend — no historical data yet, since this just started recording.

verified

DeepSeek usage is blocked at the actual call site now: DeepSeekLLMClient.__init__ (harness/llm_client.py) refuses to construct unless infra/deepseek_governance_approval.yaml carries a real sign-off — not just auto-fix-dev.yml's CI step, which was the only thing enforcing it until this review caught that nothing stopped a local run or a different workflow from skipping straight to the client. It does not mean the actual data-governance approval has happened; that's still a real decision someone has to make and record.

verified

main now has a branch-protection ruleset requiring a pull request and a passing validate check — confirmed by actually pushing straight to main twice: once with the ruleset Disabled (the push succeeded, exposing that the first setup attempt hadn't taken), once with it Active (GitHub rejected it: GH013: Repository rule violations, naming both the missing PR and the missing status check). The gate in Fig. 1 is enforced now, not just convention.

verified

Turning on that branch-protection rule immediately surfaced a real bug, hit live on a real PR: requiring validate while uat-to-prd-gate.yml was still path-filtered to procs/**.sql/tests/**.yaml meant a docs-only PR could never satisfy it — the check had nothing to run, so it sat as "Expected — waiting for status to be reported" forever, with no way to merge. Fixed by removing the workflow's path filter and moving the condition inside the job: a git-diff check decides whether to actually re-validate or just report "nothing to validate," but the job itself — and the required check — always completes.

verified

Guardrails hardened after comparing against a sibling project (bank-data-agent-eval) built specifically to attack an LLM agent: guardrails.py now catches a second statement smuggled in after a procedure's closing END (the "must start with CREATE OR ALTER PROCEDURE" check alone never saw it), and rejects any reference to a table on a new PII blocklist (infra/blocked_tables.yaml, empty by default). A fix's rationale and SQL are scanned for an email/SSN/phone shape and withheld — not just logged — before either could reach a report or a commit message. infra/guardrail_attacks.yaml + tests/test_guardrail_attacks.py is this project's first adversarial test suite: 13 catalogued attack payloads, each asserted caught, where there were previously zero.

worth noting

The attack catalog proves the guardrail catches each payload when fed to it directly — it does not prove a real LLM would never find some different way to construct a candidate that evades them, the way bank-data-agent-eval's harness actually runs its attacks through a live model and measures what got past it. This repo has no equivalent of that live-agent attack loop yet.

not yet real

Every procedure and golden figure so far is synthetic — generated test data, not a real company stored procedure or a number a business user actually checked.

not yet real

Validated against Azure SQL Database, not an actual Synapse dedicated/serverless pool — and only ever exercised against a single real procedure. The multi-procedure manifest and per-procedure round cap are unit-tested and hand-simulated, never proven against two or more real procedures in live CI.
